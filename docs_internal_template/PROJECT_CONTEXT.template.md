# Internal Project Context Template

> **이 파일은 공개 가능한 템플릿이다.** 실제 회사 / 브랜드 / 광고주 / 매체사 / 사람 이름,
> 실제 운영 사례, 메신저 본문, 정산 내역 등은 절대 적지 않는다.
>
> 작성 방법
> 1. 이 파일을 `docs_internal/PROJECT_CONTEXT.md` 로 복사해 사용한다.
> 2. `docs_internal/` 은 `.gitignore` 에 의해 추적에서 제외되므로, 복사 후 작성한 내용은
>    GitHub 으로 올라가지 않는다.
> 3. 그래도 작성 시에는 가능한 한 비식별화된 표현을 사용한다.
>    예: `작성자` / `검토자` / `담당자` / `광고주` / `매체사` / `재무팀` / `브랜드 A`.
> 4. 외부에 공유해야 하는 일반적 정보는 이 템플릿이 아니라 README.md 에 직접 정리한다.
>
> 금지 사항
> - 사람 실명, 팀명 / 부서명, 사내 도구명 / 시트명
> - 회사 / 광고주 / 매체사 / 협력사 실명
> - 실제 캠페인명 / 정산 금액 / 정산 일자 / 결재 정보
> - 메신저 본문 / 메일 본문 / 운영 사례를 그대로 옮기는 것
> - 사내에서만 통하는 약어 / 코드 / 시스템 이름

---

## 1. 목적

- 이 RAG 시스템을 어떤 사용자 / 어떤 업무 / 어떤 의사결정 흐름에 쓰려는지 한 두 줄로
  적는다.
- 답변 품질의 1차 평가 기준 (예: "체크리스트 누락이 줄어드는가") 을 적는다.

## 2. 담당 업무 범위

- 어떤 업무 카테고리를 다루는가 (예: 광고 운영 보조, 정산 보조, 보고서 보조).
- 다루지 않는 업무는 무엇인가 (예: 인사, 재무 단독 의사결정).

## 3. 데이터 소스 설명

- 어떤 종류의 자료를 어떤 카테고리로 적재하는가.
- 각 자료가 공식 가이드인지, 실무 히스토리인지, 표 기반 정의서인지 구분.
- 예시는 `브랜드 A 가이드`, `매체사 운영 안내`, `광고주 공유 문안` 처럼 일반화해 적는다.

| 카테고리 | 자료 성격 | 비식별화된 예시 |
| --- | --- | --- |
| 가이드 | 공식 절차 / 매뉴얼 | "신규 캠페인 셋팅 가이드 (브랜드 A)" |
| 메신저 스레드 | 실무 진행 로그 / 이슈 / 결정 | "당일 운영 TODO 정리" |
| 메신저 내보내기 | 잡음 많음 | "광고주 채널 대화 텍스트" |
| 표 자료 | 정의서 / 정산 시트 | "정산 항목 정의서" |

## 4. 파일 유형별 처리 원칙

- 가이드 → 공식 절차 근거. KnowledgeCard `workflow / checklist / glossary /
  communication_template` 우선.
- 메신저 스레드 → 실무 히스토리. `issue / decision / checklist / faq /
  communication_template` 우선.
- 메신저 내보내기 → source_weight 낮음. fallback 위주.
- Excel → raw + 한국어 의미 요약 이중 색인 + parent-child retrieval.

## 5. 운영상 주의사항

- 비용 통제: `ENABLE_LLM_NORMALIZATION` / Excel 요약 / Query Rewrite 의 ON/OFF 조합과
  cache 동작을 정리.
- prompt 변경 시 prompt_version 라벨 갱신 정책.
- 디버깅 모드 (`SHOW_RAW_CONTENT=true`) 사용 시 캡처 / 외부 공유 / 외부 API 호출 차단.
- 색인 / Vector DB 초기화 (`scripts/reset_vector_db.py`) 사용 시 `data/raw/` 보존 여부.

## 6. 민감정보 비식별화 규칙

- 사람 이름 → "작성자" / "검토자" / "담당자 A" 등 역할 표현.
- @멘션 → "@담당자" 등.
- 정확한 시간 → "오전" / "오후" / "퇴근 전".
- 정확한 날짜 → "해당 업무일" / "전일" / "다음 업무일" / "월초" / "월말".
- 광고주 / 캠페인 / 매체사 / 결재 번호 → "광고주" / "캠페인" / "매체사" / "결재 번호".
- 링크 / 이미지 / 파일명 → `[링크]` / `[이미지]` / `[파일]`.

## 7. 금지 사항

- 실명 / 사내 도구명 / 사내 시트명 / 광고주명 / 캠페인명 / 정산 금액을 적지 않는다.
- 외부 Vector DB / 외부 LLM / 외부 메신저 API 도입을 추가하지 않는다.
- `data/raw/` 폴더 내 파일을 GitHub 에 push 하지 않는다.
- 회사 보안 정책에서 외부로 보내면 안 되는 텍스트는 업로드 전에 사용자가 직접 마스킹 한다.

## 8. 추후 확장 아이디어

- KnowledgeCard 정규화를 어떤 데이터 소스로 확장할지 (예: 메일, 카카오 내보내기, 결재 문서).
- 어떤 평가 지표를 자동화할지 (retrieval hit rate, answer groundedness, 사용자 피드백).
- 어떤 reranker 를 추가로 검토할지 (Gemini reranker, cross-encoder).
- 어떤 hybrid retrieval (BM25 + vector) 가 적합할지.

## 9. 변경 이력

- 의미 있는 prompt / 비식별화 정책 변경 시 한 줄로 적어 둔다.
- 예: `YYYY-MM-DD — Task X 변경. (간단한 동기 / 의도)`.
